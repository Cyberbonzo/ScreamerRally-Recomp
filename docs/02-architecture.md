# 02 — Architecture: how the original game will run natively

## 1. The approaches considered

| Approach | What it means here | Verdict |
|---|---|---|
| **Static recompilation** (x86 → C / LLVM → x64) | Lift all 830 KB of x86-32 code, emulate flags, the x87 stack, string ops, self-written ISRs | Possible, but high risk for no gain: indirect jumps and data-in-code need a fallback interpreter, and x87 80-bit precision must be emulated exactly or the physics drifts |
| **Dynamic binary translation / interpreter** | A CPU emulator core | Rejected as the final runtime (this is what DOSBox already is) |
| **Reimplementation** | Rewrite the game | Rejected: it throws away the original code |
| **Native execution + purpose-built compatibility layer** | The original x86-32 machine code runs **directly on the CPU** inside a 32-bit Windows process. Everything the code expects from DOS, DOS/4GW, the BIOS, the hardware and the 3dfx/HMI drivers is reimplemented natively | **Chosen** |

Why native execution is the right kind of "recompilation" for this game: the source and
target instruction sets are the same (x86-32 runs natively on every Windows 10/11 PC
through WOW64). Translating instructions that already run on the host would only add
risk. What has to change is everything *around* the instructions: memory layout, the OS,
interrupts, I/O ports and drivers. So the translation reduces to:

1. **relocation**: load the LE image at a new base and apply its fixups;
2. **targeted rewriting**: replace the few instruction kinds that cannot run in user mode
   (`int`, `in`/`out`, `cli`/`sti`, DOS/4GW selector loads) with calls into the runtime;
3. **library replacement**: swap whole statically linked libraries that talk to obsolete
   hardware (Glide, HMI SOS, the DOS/4GW DLL loader) for native implementations, at
   function granularity.

This is the same philosophy as the reference project (*"the game's own x86-64 code runs
directly on your CPU, with no CPU emulation"*, system libraries reimplemented, GPU commands
translated). The game logic, physics, AI and x87 floating-point arithmetic are the
original instructions executed bit-for-bit, so handling cannot drift.

## 2. Process layout

```
ScreamerRally.exe  (32-bit Windows process, i686)
├─ Launcher / settings UI ─────────────── first run: pick disc folder or image, validate
├─ Game-data layer ────────────────────── MDF/MDS · CUE/BIN · ISO · folder → virtual drive D:
├─ Loader ─────────────────────────────── LE parse → map objects → fixups → patch plan
├─ Guest thread (original code) ───────── runs STRT3FX.EXE natively
│    ├─ Trap layer      vectored exception handler: int / in / out / cli / sti /
│    │                  selector loads / low-memory faults → emulate → resume
│    ├─ Patch layer     hot trap sites rewritten into direct calls (optimisation only)
│    └─ HLE services    DOS int 21h · DPMI int 31h · BIOS 10h/16h/1Ah · mouse 33h ·
│                       MSCDEX 2Fh · VDS 4Bh · PIC · PIT · 8042 keyboard · gameport
├─ Library replacements (function hooks)
│    ├─ Glide 2.x  → renderer        (all 100 imported entry points)
│    ├─ HMI SOS    → audio mixer     (digital samples, timer service, MIDI)
│    └─ DOS/4GW DLL loader → returns native Glide
└─ Platform services (Rust)
     ├─ Window, DPI, windowed / borderless / exclusive fullscreen (desktop mode only)
     ├─ Renderer   Direct3D 11, flip-model swap chain (tearing, VSync, FPS cap)
     ├─ Audio      WASAPI shared mode, float mixer, CD-DA streamer, SFX/music volume
     ├─ Input      XInput (+ HID later), keyboard, mapping, dead zone, sensitivity
     └─ Config     TOML settings, persisted next to the exe
```

A separate 64-bit helper process is reserved for NVIDIA DLSS / Frame Generation / Reflex
later on, because those SDKs only ship 64-bit binaries (see §8).

## 3. Execution model

* The guest runs on its own thread. Its stack lives inside a host-allocated region and
  the thread's TEB stack bounds are set to cover it, so Windows exception dispatch works
  while guest code is running.
* Host → guest calls and guest → host calls go through small assembly thunks that convert
  between the Win32 stdcall/cdecl conventions and Watcom's register convention
  (`EAX, EDX, EBX, ECX`), and save/restore `FS` (Win32 TEB) and the x87 control word.
* **Interrupts** are virtual. The runtime keeps a virtual IF flag (`cli`/`sti` are
  trapped or patched), a virtual 8259 PIC and a virtual 8253 PIT. Hardware interrupts
  (timer, keyboard) are delivered to the game's own handlers by building an `iretd`
  frame on the guest stack when the guest is in a safe state; the handlers then return
  natively with `iretd` (verified to work at ring 3).
* **Time** is generated by the host. The game's clock is a 100 Hz tick (HMI SOS timer
  event), so the runtime decides exactly when each tick happens. This gives
  (a) wall-clock-correct speed at any frame rate, and (b) a fully deterministic mode
  for regression tests.

## 4. Memory model

* LE objects are relocated to a reserved region (default base `0x10000000`) with all
  pages read/write/execute (the game stores its key-state table inside its code object).
* **Conventional memory is virtual.** Windows already uses the bottom megabyte of every
  process (verified), so DOS memory blocks, the PSP, the environment and the BIOS data
  area live in host memory, while the segment values handed to the guest point below
  `0x10000` — an address range Windows never maps. Every flat access to "conventional
  memory" therefore faults and is redirected by the trap layer; every selector-relative
  access with a small offset faults the same way.
* **Selectors.** WOW64 cannot create LDT descriptors and resets segment registers to
  the flat selectors on every exception return (verified). So every selector handed out by
  the DPMI emulation is a base-0 alias of the flat segment, and the few places that rely
  on a non-zero base are found statically (a scan of the disassembly lists them) and
  patched. Nearly all of them sit inside the libraries that get replaced anyway.

## 5. Rendering

The 3dfx build (`STRT3FX.EXE`) is the primary target, because all its drawing goes through
Glide 2.x. Glide vertices are floating-point screen coordinates with `1/w`, `s/w`, `t/w`:

* **Resolution**: the game renders for 640×480 (to be confirmed from `grSstWinOpen`);
  coordinates are scaled to any output size, so geometry gets sub-pixel precision instead
  of an upscaled image. Up to 4K and beyond.
* **Perspective-correct texturing**: Voodoo hardware was already perspective-correct;
  reproducing it exactly in a pixel shader removes the warping of the software builds.
* **Filtering**: `grTexFilterMode` is overridable — nearest-neighbour (default) or
  bilinear — with Voodoo mip-mapping semantics preserved.
* **2D / HUD**: LFB writes (`grLfbLock`, `grLfbWriteRegion`) go to a 640×480 RGB565
  surface composited with integer or aspect-correct scaling, so menus stay sharp.
* **Ultrawide**: needs the game's own camera to produce a wider frustum. This means
  patching its projection and clip constants, which requires reverse engineering the
  camera code (Phase 3). The HUD stays at 4:3 in the centre or is anchored to the edges.
* **Highest LOD / draw distance**: the game's LOD selection and far-clip constants are
  located by RE and overridden (Phase 3). No new geometry is created.
* **API choice: Direct3D 11.** It is the most stable API for a 32-bit process on
  Windows 10/11, maps Glide's fixed-function state onto a handful of shaders, and easily
  runs this triangle load at thousands of FPS. The flip-model swap chain gives uncapped,
  capped and VSync modes and VRR.

## 6. Frame rate independent of simulation

What the game does (RE notes, "Timing"): one loop iteration = simulate one step, then draw.
The step is the time since the previous frame (smoothed, x1.1 in races) with a floor of
0.02 s, so above 50 frames per second the original runs faster than real time (2x at 100
fps). The runtime therefore paces the loop to 20 ms per iteration (two ticks of the 100 Hz
timer): the simulation runs exactly as designed (verified against the game's own real-time
and simulation clocks).

**Interpolated frames** (`interp.rs`, on by default, `graphics.interpolate`): in races
the runtime draws its own frames between the game's steps, so the picture moves at the
display's rate (VSync) or as fast as the PC allows (VSync off, optional limit), while the
game itself still simulates 50 steps per second.

* The game's draw step is `34af4`: camera set-up `236dc`, world and cars `349b8`, HUD
  `4e224`, mirror, then the buffer swap. When the HUD starts, the runtime takes the main
  camera (the structure at `[81e0c]`: three 11-bit angles, position, a Q14 rotation matrix
  and its transpose) and every scene object (the table at `12f860`: cars, wheels, shadows,
  smoke and marks, each with a position and three angles). The game's own present is
  suppressed; everything it draws from the HUD on (HUD, mirror, pause menu) is recorded.
* Between that step and the game's next frame (paced from the frame's start, 20 ms), the
  runtime repeatedly calls `set_view` and `349b8` itself, with camera and objects set to
  values interpolated between the previous and the current step (angles the short way
  round; the rotation blended and re-orthonormalised), replays the recorded HUD on top and
  presents. The picture is therefore one step (20 ms) behind the simulation. Camera cuts
  (big moves or turns), steps not following each other (menus, loading) and objects that
  jump (a reused smoke slot, a reset) are shown as they are instead of being swept.
* Drawing is not free of side effects (the camera code, the car drawing at `2d0bc` writes
  car state, segment translation patches code), so guest memory is protected: every
  allocation the guest gets is made with `MEM_WRITE_WATCH`. Once per step the runtime
  copies the pages the game wrote into a shadow; after each extra frame it puts back every
  page the drawing wrote (`GetWriteWatch`), about 90 pages a frame. Code translated during
  an extra draw is kept (in memory and in the shadow). Timer and keyboard interrupts are
  held while an extra frame is drawn (none is delivered while the guest thread is in the
  runtime anyway), sound calls do nothing, so the game cannot observe the extra frames.
* VSync on: a frame is drawn only when the swap chain can take it without blocking (the
  frame-latency waitable object, latency 1), and never after the game's next frame is due,
  so presenting can never slow the game down. VSync off: frames as fast as possible, or
  evenly spaced at the frame rate limit (`graphics.fps_cap`).
* Cost (RTX 3090 class PC, 1280x720 window, 300 % draw distance): ~1.2 ms per extra frame
  (game drawing 0.7-0.9 ms, memory restore 0.2 ms, present 0.06 ms), so a race shows
  ~900-1000 frames per second with VSync off. Measured with `SR_SAMPLE=1` (a sampling
  profiler in the runtime). Getting there needed the Glide layer to stop doing per-call
  work (string formatting for disabled log levels, per-call clocks, state changes that do
  not change anything flushing the batch) and the HUD's LFB images to be uploaded once
  per step instead of once per frame.
* Verified: frame dumps of consecutive interpolated frames (`SR_INTERP_STEPS=n` draws n
  evenly spaced frames per step) show cars and camera moving smoothly (a car's edge moves
  2-3 pixels per frame, monotonically); the simulation stays at 50 steps per second with
  VSync off, on, and with a limit (144 presents per second at a 144 limit); a 90 s race,
  the pause menu, restarting and quitting a race work. Not judged by eye on a real
  display in this session.
* Proof that the extra frames are invisible to the game: in deterministic mode
  (`SR_DETERMINISTIC`, virtual time and fixed memory addresses) a
  scripted race run with interpolation on ends with every scene object (cars, wheels,
  shadows, smoke) byte-identical to the same run with it off, and with no differences in
  game data beyond those two plain runs already show (3D render scratch).
* Interpolating the Glide vertex stream instead is not workable: the engine's clipping,
  culling and sorting change the stream from frame to frame, so vertices cannot be matched.

## 7. Audio, CD music and input

* **Sound effects**: the HMI SOS digital API is replaced at function level. By default
  the voices are mixed as the game asks HMI's driver to (11025 Hz, nearest sample,
  saturating mix, each sample held for four 44.1 kHz frames), with the original volumes
  and pans, scaled by the user's SFX volume; a full-rate mode is available.
* **MIDI** (HMI MIDI driver with OPL FM banks): unused. The game's song loader has no
  callers and its data contains no songs (RE notes); the driver is only initialised when a
  music card is configured, which the runtime does not do.
* **CD music**: MSCDEX device-driver requests (play, stop, resume, Q-channel position,
  volume) are emulated. Audio is streamed straight from the user's image (MDF/BIN) or from
  ripped WAV/FLAC files, with its own volume.
* **Keyboard**: host key events are fed into the virtual 8042, so the game's own IRQ1
  handler and key table work exactly as in 1997.
* **Controller**: the game already reads an analog joystick through the gameport. XInput
  sticks and triggers feed a virtual gameport with real analog values (dead zone,
  sensitivity and response curve applied first), so steering, throttle and brake are
  genuinely analog through the game's own input code. How throttle and brake map to the
  gameport axes is still to be reverse engineered.

## 8. DLSS, Frame Generation and Reflex

NVIDIA's DLSS (NGX/Streamline) and Frame Generation SDKs ship only 64-bit binaries, while
the original code needs a 32-bit process. If they are worth it, the renderer can move
into a 64-bit helper process that receives the Glide command stream through shared memory
(~µs latency). The geometry is generated by our renderer, so depth and exact per-vertex
motion vectors can be produced reliably.

**Honest assessment (updated):** a race frame costs ~1-3 ms of runtime work and only
~1-3 k triangles, so native 4K and beyond already run far faster than any display:
DLSS Super Resolution brings nothing, and DLAA would work against the sharp-pixel look.
Reflex helps when the GPU is the bottleneck, which it is not here. Frame Generation is
not needed either: the interpolated frames of section 6 already reach the display's
refresh rate (or ~1000 frames per second without VSync) with exact geometry instead of
generated pixels. Conclusion: no DLSS component is worth shipping; the 64-bit helper
process would add latency and complexity for no visible gain.

## 9. Language and toolchain

* **Rust** for the runtime, compatibility layer, renderer, audio, input, config and tools,
  built for `i686-pc-windows-msvc`. Small `global_asm!` thunks handle the guest boundary.
* Dependencies are kept to well-known crates: `windows` / `windows-sys` (Win32, D3D11,
  WASAPI, XInput), `iced-x86` (instruction decoding for the trap layer and patcher), and
  later a small immediate-mode GUI for the settings overlay.

## 10. Supported versions and validation of files

* Supported now: the Italian Milestone CD in this folder (hashes in
  `01-investigation.md`).
* Hooks are located by **byte-pattern signatures checked at load time**, not by raw
  addresses, so other releases (the English Virgin CD, network builds) can be added by
  checking the signatures against them. Unknown executables are refused with a clear
  message instead of being run with wrong patches.

## 11. Fidelity validation

* **Determinism first**: with host-generated ticks and recorded input per tick, a run is
  reproducible. Per-tick dumps of the car, camera and AI state are written to a trace.
* **Reference traces from the original**: the same input recording is replayed in
  DOSBox-X (development tool only, never shipped), and its debugger dumps the same
  structures on each tick callback. A comparison tool diffs the traces (acceleration,
  braking, steering response, collisions, AI paths, lap times, camera).
* The game's own replay files (`REPLAYS\*.RPL`) are a second source of comparison data.
* Renderer: golden-image tests of the Glide implementation and checks that the vertex
  stream sent to Glide is unchanged between versions.
